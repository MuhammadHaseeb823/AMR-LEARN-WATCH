Page 01 · Rule-based microbiology logic

Laboratory Intelligence

Versioned rule interpretation of AST results. The case generator is for practice and demonstration.

This module never predicts susceptibility from an image or an organism's identity alone. Real antimicrobial susceptibility testing (AST) requires physically exposing a grown isolate to each antimicrobial (disk diffusion or broth microdilution) — this tool interprets S/I/R results you already have, using deterministic logic loosely informed by EUCAST expert-rule concepts. It also includes an illustrated identification exercise, because in a real workflow the organism is identified from culture before susceptibility is ever tested.

How this actually works — no shortcuts. Stage A below is an interactive diagram-based exercise (drawn illustrations, not photographs, and not automated image recognition) that mirrors real presumptive-identification reasoning: Gram stain → culture appearance → confirmatory biochemical test → presumptive organism. Stage B then asks you for real (or practice) AST results and interprets the pattern. Nothing here diagnoses a patient or replaces a biomedical scientist.

Experimental image analysis threshold and blob counting, not a trained model

This does not identify organisms. It reports image quality, candidate objects and a colour-based suggestion for a human to check. Detection confidence varies with photo quality, and results are experimental.

Upload any plate photo and this runs genuine, real-time image processing entirely in your browser (nothing is uploaded anywhere): a blur/brightness/contrast quality check, then simple threshold-based blob counting. This is not a trained deep-learning model and will be far less accurate than one on a real cluttered clinical plate — it exists to demonstrate the pipeline honestly, not to replace laboratory identification.

Page 02 · Statistical detection, not machine learning

Surveillance Intelligence

Statistical detection of resistance trends. The series generator is for practice and demonstration.

Simulates a 24-month resistance-proportion series and runs it through three named, classical statistical detectors side by side — a moving average, EWMA, and CUSUM — rather than one arbitrary threshold. None of these are trained machine-learning models; they are transparent, reproducible formulas, which is a deliberate and more defensible design choice for a screening tool.

Simulation controls

Onset months are fixed per scenario so a "detection delay" can be computed for each algorithm — a demonstration metric, not a validated clinical statistic.

Page · Computed live, in your browser, from the current seed

Validation

Generates a batch of seeded synthetic cases and computes real accuracy/sensitivity/false-alarm metrics against them — the same honest pattern used in the full research build, just computed on the spot instead of pre-baked. Read the caveat below before citing any number.

What these numbers do and don't mean. The laboratory "ground truth" here is whatever the same deterministic rule engine outputs for that AST pattern — there is no independent wet-lab oracle in a browser. Near-100% laboratory accuracy is a self-consistency check, not evidence of real diagnostic performance. The early-warning comparison is more informative: sensitivity, false-alarm rate and detection delay genuinely differ between the three statistical detectors on the same generated data.

About this system

        

          What is actually AI here, and what isn't?
          

            Rule-derived Laboratory identification and AST interpretation — fixed decision logic, no learning, fully reproducible.

            Statistical Early-warning detection (moving average / EWMA / CUSUM) and stewardship trend audit — classical formulas, not trained models.

            Generative (optional) Plain-language rewriting of a rule-derived finding, only if you supply an API key — it explains, it does not decide.

            Uncertain Shown whenever evidence is missing, contradictory, or outside this tool's organism list, instead of guessing.
          

          
No component here is a trained, validated machine-learning classifier. Calling the whole system "AI-powered" without that distinction would overstate what it does — so this page states it plainly instead.

        

        

          Data, ethics & reproducibility
          
All data is synthetic, generated in your browser, and nothing is transmitted anywhere unless you explicitly enable the optional generative layer. Session data (tallies, findings, audit trail) is saved only to this browser's local storage on this device — not to any server, not synced across devices, and visible to no one else. No patients, biological specimens or human participants are involved, so this computational demonstration would not typically require research ethics approval — but that determination should still be confirmed with your institution before any results are used in a publication. Random generation is seeded: setting the session seed (Evidence page) and repeating the same actions in the same order reproduces identical practice cases, series and results. Generative explanations and server data are not reproducible by seed.

        

        

          Current limitations / roadmap
          
This single-file version does not include: a trained ML model (the optional image analysis on the Laboratory page is classical computer vision — thresholding and blob counting — not a learned model), a locked validation dataset with ground-truth labels, sensitivity/specificity/F1 benchmarking, multi-user accounts, or a persistent server-side database. Those need a real backend and are a natural next phase, not something a static HTML file run in one browser can honestly claim to do.

          External data sources — what's live, what isn't, and why
          
This project started from a plan to use real public datasets (Dataset19 on Zenodo, CC BY 4.0) and real third-party tools (AMRIE, R AMR, Cellpose). Here's exactly what a static file like this one can and can't do with each:

          
    
            
  • Dataset19 metadata — Zenodo's file API supports direct browser fetches for small files. The button below attempts a live fetch of that dataset's real record metadata, right now, in your browser.
    • 
            
  • Dataset19 images — not fetchable in practice: the real photos are bundled in one 5.6 GB archive, not separate files, so "loading a real photo" would mean your browser downloading the entire archive first. Not attempted here.
    • 
            
  • AMRIE / R AMR / Cellpose — these are software packages, not web services. No browser trick reaches them; they need a real .NET, R, or Python/GPU runtime respectively. The separate FastAPI/PostgreSQL backend project delivered earlier in this project (AMR-LabAI.zip) has real, currently-mocked-but-swappable adapters for exactly this — this single HTML file architecturally cannot.
